# AI Usage

This document describes the use of AI assistants during development of this project, as required by the Azatech Technical Test guidelines.

## Tools Used

- **AI Assistant**: Kiro (Claude-based AI) running in the Kiro IDE
- **Model**: Auto (dynamically selected)

## Parts Built with AI Assistance

The entire codebase was scaffolded and implemented with AI assistance:

1. **Project structure**: Monorepo setup with pnpm workspaces, NestJS API, and Next.js web app
2. **Database schema**: Prisma schema design for all tables (users, products, customers, orders, order_items, stock_movements, idempotency_keys, refresh_tokens)
3. **Seeder**: Seed script generating 1 admin, 1 cashier, 50 products, 30 customers, and 150 orders across 90 days
4. **Backend modules**: Auth (JWT + refresh rotation), Products (CRUD + stock adjustment), Customers (CRUD), Orders (state machine, concurrency, idempotency), Reports, Dashboard, Health, Queue workers
5. **Common infrastructure**: Exception filter, response transform interceptor, request-id interceptor, RBAC guards, pagination DTO
6. **Frontend**: Login page, dashboard with sidebar navigation, products list/detail, customers list, orders list/create/detail, reports page with charts
7. **Infrastructure**: Docker Compose, multi-stage Dockerfiles, GitHub Actions CI pipeline
8. **Testing**: Unit tests for order state machine, E2E tests for auth, products, orders, idempotency, concurrency, RBAC
9. **Documentation**: README.md, ARCHITECTURE.md, this file

## Key Prompts Used

1. "buatkan project dengan sesuia ketentuan dan sesuia permintaan test dialam sini ya" — followed by the full Azatech technical test specification. This was the initial prompt that set the scope and all requirements.

2. "baik lanjutkan lagi hingga selesai" — instruction to continue building until the project was complete, covering all remaining files from frontend pages through Docker, CI, and documentation.

## Parts Written or Modified by Hand

All code in this repository was generated by the AI assistant based on the technical test specification. The developer reviewed the output and made the following decisions:
- Chose Track A (NestJS + TypeScript) over Track B (Laravel)
- Chose pessimistic locking over optimistic locking for stock concurrency
- Chose database-backed idempotency over Redis-only
- Chose 422 for idempotency key payload mismatch (not 409)
- Database schema design decisions (BigInt IDs for products/orders, UUID for customers, soft delete pattern)
